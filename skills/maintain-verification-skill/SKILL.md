# Maintain a verification skill

Version: 1.0.0 (2026-10-12)

A feature map rots the moment the app changes. This is the upkeep loop for a skill generated by `/create-verification-skill`, or any project-local verification skill with a feature map. The unit of rigor is the feature, not the sentence. Cover every feature file from source and exercise every feature live, without turning every bullet into a terminal command.

## Outcomes

Pick one, and say which:

- **clean.** Every feature got source and live coverage, and nothing is worth shipping. No branch, no PR.
- **changed.** One PR ships proven doc, harness, or map corrections.
- **blocked.** Coverage couldn't finish, or a proven fix couldn't ship safely. Say exactly what blocked it.

## Edit scope

Edit only the verification skill's own directory: its SKILL.md, `features/`, and any harness scripts it owns. Never edit product code during a run. When the map describes behavior the app no longer has, that is either doc drift (fix the map) or a product regression (report it, don't paper over it in docs).

## Pass

0. **Locate the target.** Find the project-local skill whose body has Launch and Drive sections and a feature map, usually `.claude/skills/verify-*/`. Several candidates: ask which one. None: stop and point at `/create-verification-skill` instead of inventing a target.

1. **Index hygiene.** Read the feature map README and glob its sibling files. Fix missing, extra, duplicate, or dead entries. Keep it light. Don't generate an inventory.

2. **Source wave.** Spawn one read-only subagent per feature file, all in a single message so they run concurrently:
   - `subagent_type`: `Explore`
   - `model`: `sonnet`
   - Prompt: the feature file's path and contents, the repo root, and this brief. "Explain how this user-facing feature works, from source. Flag likely drift between the feature file and the code, citing file paths and lines. Return one concise live-verification recipe. Don't run the app and don't edit files. Return four parts: feature summary, source entry points, likely drift (or none), one recipe."

   If you can't spawn subagents, do the same reading inline, one feature at a time.

3. **Reconcile.** Check that every feature file has a returned summary. Merge overlapping recipes into as few app states as practical. Spot-check cited drift against the code. Don't re-prove clean claims. Sweep recent churn (`git log` since the skill's last change) for user-facing surfaces missing from the map. Require a concrete source path before you call one missing.

4. **Live pass.** Required even when the source looks clean. You own all driving. Subagents don't drive. Follow the verification skill's own launch model: one long-lived instance driven serially for servers and UIs, or a fresh isolated session per drive for short-lived CLIs. The skill's Launch section decides, not this one. Exercise every feature at least once, and hold three invariants for the whole pass, whatever fails:
   1. Never drive an instance you haven't health-checked since it last did something surprising. Run doctor before the first drive, on each fresh session where sessions are the unit, and again after any failed drive. Where doctor can't see the failure (a wedged UI on a healthy process), reset to a known state or relaunch rather than hoping.
   2. Evidence captured so far survives every cleanup. Check it at its named location. Don't assume.
   3. Nothing a drive started outlives its usefulness. Clean failed-attempt residue whether the session is stuck, exited, or shared. On a shared instance, clean the residue, not the instance.

   A doctor failure caused by skill drift is drift. Fix it under edit scope and retry once, restarting only what the fix invalidated, before you call the pass `blocked`.

   A feature that can't be reached is `verified-unreachable` only with the concrete prerequisite (auth, entitlement, OS, external state) and the route you attempted. If the map omits that prerequisite, that's drift.

   Re-drive any harness fix from triage live before it ships. Do final teardown after the last drive of the run, re-proofs included, so nothing outlives the run. Evidence stays, per the skill.

5. **Triage.**
   - Wrong or missing user-POV description: doc drift. Fix it.
   - Working behavior the harness can't drive: harness gap. Fix it. A harness fix follows the same helpers rule as generation: scripts are executable and their invocation is documented in the skill body.
   - App behavior that is actually broken: product gap. Record it for the user and keep it out of this PR.

6. **Ship or stop.**
   - **changed.** Re-read every changed file. Commit on a new branch from the default branch and open one PR of proven corrections, with the coverage summary in its description. Use `gh pr create`, or the GitHub MCP tools when `gh` isn't available. If you can't open a PR, push the branch and say so.
   - **clean or blocked.** No branch, no PR. Report the outcome and the coverage honestly.

Keep short run notes (features covered, unreachable prerequisites, confirmed drift, outcome) in a scratch location outside the repo, such as the session scratchpad. Don't commit them.

## Reply

Lead with the outcome. Then one line per feature: covered from source, driven live or `verified-unreachable` with its prerequisite, and any drift fixed. List product gaps separately. Link the PR if there is one, and say where the evidence is.

## Running it on a schedule

The pass only helps if it runs after the app changes. If the user asks for a cadence, a Routine (scheduled trigger) or `/loop` can fire it. Each firing needs a session that can launch the app, so a cloud environment's setup script must install what Launch depends on.
