# Phase-1 skill evals, 2026-10-05

A/B tests of unslop, technical-writing, reflect, and deslop (second fixture), plus a trigger-routing test of all four descriptions. Per-run outputs, `grading.json`, `llm_grading.json`, and `timing.json` live under `evals/<skill>/results/2026-10-05/`. Regenerate the tables with `python3 evals/aggregate.py <skill>`.

## Method

- **Runner.** `evals/run_ab.py` starts each run as a separate `claude -p --model <haiku|sonnet|opus>` process (CLI 2.1.289) in a fresh work directory with a throwaway `HOME`. That means no user skills, plugins, or memory, and no session persistence. The Agent tool wasn't available to the orchestrating session, so this replaced subagents.
- **Arms.** The skill arm copies `skills/<name>/` into `<work>/.claude/skills/` and appends "Use the <name> skill." The baseline arm installs nothing and appends "Do not load or invoke any skill." Built-in Claude Code skills stay visible in both arms. Every skill-arm run loaded its skill, and no baseline run loaded one ("Skill loaded" column).
- **Cells.** Haiku 4.5 and Sonnet 5.5 for every skill, plus Opus 5.5 for deslop's new fixture, reflect, and unslop, with 3 runs per cell. No cell was skipped for saturation, because the Sonnet and Opus ceilings only became clear after grading.
- **Fixtures avoid the skill's own examples.** Each grader's docstring lists what is seeded. None of the seeded problems is named in the matching `SKILL.md`, except checks marked `[named]` (for example, sentence-case headings), which the tables still count.
- **Grading.** Deterministic checks come first (AST, tokenize, regex, and the fixture's behavior script). Where judgment is needed, a blind rubric is graded by a separate `claude -p --model sonnet` call with no tools. It sees the rubric, the original, and the output, but never the arm, the model, or the path (`evals/llm_grade.py` and `evals/reflect/grade.py --llm`). "Det." and "LLM" are reported separately.
- **Tokens.** Each run's tokens are the sum of input, output, cache-read, and cache-creation tokens over every model in `modelUsage`, including Claude Code's own small-model calls. This is not the same metric as the 2026-10-03 subagent `total_tokens`, so compare within this report only. All 66 A/B runs together used about 9.8M tokens, not counting the grader, trigger, or debugging calls.

## unslop: `build-times-post`

The fixture is a 365-word team blog post with 12 seeded tell clusters. It also carries things that must survive: every number, a code block, a quote that says "game changer" on purpose, and a refrain ("Measure, then cut.") that appears three times on purpose. The rubric items are meaning_preserved, no_new_tells, reads_human, and tone_matches. Leaving the post untouched scores 5/18, and the reference rewrite scores 18/18.

| Model | Arm | Det. mean | Det. per run | LLM mean | LLM per run | Tokens (mean) | Time (mean) | Skill loaded |
|---|---|---|---|---|---|---|---|---|
| Haiku 4.5 | no skill | 85% | 83%, 83%, 89% | 50% | 50%, 50%, 50% | 247,909 | 27s | 0/3 |
| Haiku 4.5 | skill | 89% | 89%, 83%, 94% | 50% | 50%, 50%, 50% | 285,587 | 34s | 3/3 |
| Sonnet 5.5 | no skill | 93% | 89%, 94%, 94% | 67% | 75%, 75%, 50% | 103,190 | 12s | 0/3 |
| Sonnet 5.5 | skill | 96% | 100%, 94%, 94% | 83% | 75%, 100%, 75% | 110,161 | 15s | 3/3 |
| Opus 5.5 | no skill | 94% | 94%, 94%, 94% | 83% | 75%, 100%, 75% | 110,228 | 22s | 0/3 |
| Opus 5.5 | skill | 94% | 94%, 100%, 89% | 83% | 75%, 100%, 75% | 107,392 | 21s | 3/3 |

The skill nudges the deterministic score up by 3 to 4 points for Haiku and Sonnet, and the blind rubric favors the skill arm for Sonnet (67% to 83%: fewer new tells). Haiku's rubric score stays at 50% in both arms. It adds claims ("tanking productivity") and new stock phrasing either way. Opus scores the same with and without the skill (94%/94% det, 83%/83% LLM). No arm preserves meaning reliably: meaning_preserved fails in 15 of 18 runs, usually from one added clause of motivation or plans.

**Verdict: keep, but expect a small effect.** It helps Sonnet a little and doesn't move Opus. On Haiku it removes the listed tells but doesn't stop new ones.

## technical-writing: `cert-rotation-runbook`

The fixture is a chatty runbook for rotating a TLS cert. It buries a backup step ("I forgot to mention"), puts the month-end warning after the drain step, and states its prerequisites halfway through. The rubric items are no_invented_facts, rollback_correct, how_to_only, and first_read. Untouched, it scores 4/10. The grader is v3: v1 had 11 checks, and two artifacts were fixed (see Caveats).

| Model | Arm | Det. mean | Det. per run | LLM mean | LLM per run | Tokens (mean) | Time (mean) | Skill loaded |
|---|---|---|---|---|---|---|---|---|
| Haiku 4.5 | no skill | 90% | 90%, 90%, 90% | 67% | 50%, 75%, 75% | 99,903 | 19s | 0/3 |
| Haiku 4.5 | skill | 93% | 90%, 100%, 90% | 83% | 75%, 75%, 100% | 107,296 | 32s | 3/3 |
| Sonnet 5.5 | no skill | 90% | 90%, 90%, 90% | 75% | 75%, 75%, 75% | 103,930 | 15s | 0/3 |
| Sonnet 5.5 | skill | 100% | 100%, 100%, 100% | 75% | 75%, 75%, 75% | 137,960 | 19s | 3/3 |

Sonnet with the skill gets every deterministic check in all 3 runs, against 90% without it. The difference is sentence-case headings, a `[named]` check. On the rubric, Haiku improves (67% to 83%) and Sonnet stays flat at 75%. Every arm invents something, and no_invented_facts fails in 11 of 12 runs. The usual inventions are an escalation line ("ask in #billing-oncall") or a verification step. The skill doesn't prevent this.

**Verdict: keep.** The gain is modest and real on structure. It is not a guard against invented facts (see Recommendations).

## reflect: `pypi-release-session`

The fixture is a transcript of a release session. It contains a dead end (bumping the version in `pyproject.toml` when the project reads it from `__about__.py`) and a user correction (stale `dist/` wheels, then `--skip-existing`, which the user stopped). It also includes an unused `docker-deploy` skill, a typo, and a 429 aside as distractors. The rubric items are version_source_routed, stale_dist_routed, concrete, no_invented_learnings, and no_edits_claimed. Neither the dead end nor the correction appears in the reflect `SKILL.md`.

| Model | Arm | Det. mean | Det. per run | LLM mean | LLM per run | Tokens (mean) | Time (mean) | Skill loaded |
|---|---|---|---|---|---|---|---|---|
| Haiku 4.5 | no skill | 100% | 100%, 100%, 100% | 80% | 100%, 60%, 80% | 130,848 | 30s | 0/3 |
| Haiku 4.5 | skill | 88% | 88%, 88%, 88% | 80% | 100%, 80%, 60% | 143,226 | 39s | 3/3 |
| Sonnet 5.5 | no skill | 100% | 100%, 100%, 100% | 93% | 80%, 100%, 100% | 120,911 | 18s | 0/3 |
| Sonnet 5.5 | skill | 100% | 100%, 100%, 100% | 93% | 100%, 80%, 100% | 153,555 | 15s | 3/3 |
| Opus 5.5 | no skill | 100% | 100%, 100%, 100% | 100% | 100%, 100%, 100% | 123,986 | 31s | 0/3 |
| Opus 5.5 | skill | 100% | 100%, 100%, 100% | 100% | 100%, 100%, 100% | 155,545 | 31s | 3/3 |

The v1 grader showed a large lift (Sonnet 82% to 97%, Opus 85% to 100%). That lift was a grader artifact. v1 failed any output that mentioned `docker-deploy` or the typo, even when it mentioned them only to decline them, and the baseline does exactly that in prose. Grader v2 ignores declined mentions. With v2, every model finds the right two learnings and routes them to `pypi-release` with or without the skill. What the skill changes is the form of the output: an Accepted/Rejected/Backlog table about half as long (roughly 180-570 words against 250-950) that ends by asking for approval. Haiku with the skill never writes `proposals.md`, in all 3 runs. It follows step 4 ("show the full output and stop") and prints the table instead. Its deterministic score is 88% only because of that.

**Verdict: revise.** On this fixture the skill buys format and brevity, not better learnings, and it costs about 10-30k more tokens per run. To show value, it needs a harder fixture (subtler learnings, a tempting wrong routing, compaction) before porting more skills like it. The `Wrote proposals.md` miss reflects a conflict between the task prompt and the skill's "stop and wait" rule. Treat it as a fixture issue, not as a skill defect.

## deslop: second fixture, `signups`

The fixture is a branch that adds `build_attendees`/`clean_name` to a CSV sign-up module. Its slop is not among the `SKILL.md` examples: a re-implemented `normalize_email`, magic `64` and `"waitlist"` literals that duplicate existing constants, `rows = list(rows)`, `len(x) == 0`, and assign-then-return. It also contains defensive code that must stay: the `or ""` CSV guards, the `dict(row)` copy (with a why-comment), and the blank-row why-comment. Behavior is checked by the harness's own `check.py` (core, boundary, and no-mutation). Seeded, it scores 6/12, and the reference scores 12/12. The grader is v2: `int(capacity)` is no longer scored (see Caveats).

| Model | Arm | Det. mean | Det. per run | Tokens (mean) | Time (mean) | Skill loaded |
|---|---|---|---|---|---|---|
| Haiku 4.5 | no skill | 81% | 92%, 58%, 92% | 180,964 | 28s | 0/3 |
| Haiku 4.5 | skill | 83% | 83%, 83%, 83% | 326,754 | 37s | 3/3 |
| Sonnet 5.5 | no skill | 100% | 100%, 100%, 100% | 88,843 | 10s | 0/3 |
| Sonnet 5.5 | skill | 100% | 100%, 100%, 100% | 120,744 | 10s | 3/3 |
| Opus 5.5 | no skill | 100% | 100%, 100%, 100% | 152,607 | 26s | 0/3 |
| Opus 5.5 | skill | 97% | 92%, 100%, 100% | 163,968 | 25s | 3/3 |

On a fixture the skill doesn't name, deslop gives Haiku nothing measurable (81% to 83%, within noise). It does reduce variance: Haiku without the skill scored 58% once, breaking the boundary handling and both why-comments. The skill costs Haiku about 1.8x the tokens. Sonnet and Opus are at the ceiling without the skill. One Opus skill-arm run inlined `clean_name` as a single-use helper and broke `check.py`'s call to it. That counts as a behavior change only if `clean_name` is public API, which the fixture doesn't say.

**Verdict: keep for Haiku-tier only**, as the 2026-10-03 result said. That earlier 74% to 91% gain was mostly the skill recognizing its own examples: on unnamed slop the gain is about 2 points. For Sonnet and Opus it costs tokens and buys nothing on either fixture.

## Trigger routing

`evals/triggers/run_triggers.py` installs all four skills into a throwaway project and gives the child only the `Skill` tool. It records which phase-1 skill loads first and stops there. There are 38 prompts (`evals/triggers/prompts.json`): 7 unslop, 8 technical-writing, 8 deslop, 9 reflect, and 6 negatives, including near-misses across the four skills. Each prompt ran 2 times per model, and the 11 prompts whose routing changed between the current and proposed descriptions ran 4 times. v1 prompts carried no content (for example, "fix it" with nothing pasted), and models asked for the text instead of loading a skill. Those runs are archived in `results/2026-10-05/v1-prompts/` and not used. v2 prompts include the pasted content, and reflect prompts include a one-paragraph summary of the earlier session.

| Model | Descriptions | unslop | technical-writing | deslop | reflect | negatives | Total |
|---|---|---|---|---|---|---|---|
| Haiku 4.5 | current | 21/24 | 15/20 | 20/22 | 14/18 | 14/14 | 84/98 |
| Haiku 4.5 | proposed | 22/24 | 19/20 | 22/22 | 14/18 | 13/14 | 90/98 |
| Sonnet 5.5 | current | 17/24 | 18/20 | 18/22 | 14/18 | 12/14 | 79/98 |
| Sonnet 5.5 | proposed | 18/24 | 18/20 | 21/22 | 14/18 | 13/14 | 84/98 |

Findings:

- **deslop under-triggers on pasted code.** "Clean up this Python function an LLM generated" loaded deslop on Sonnet 1 time in 4 with the current description, because it says "code diff". After adding "or pasted code", it loaded 4 times in 4, and Haiku also went from 3/4 to 4/4. Applied.
- **unslop under-triggers when the user describes the symptom** ("sounds like marketing copy", "robotic") instead of saying "de-AI". The worst case was Sonnet on the status-update prompt (u5) at 1/4. After adding "when text sounds robotic, salesy, like marketing copy, or full of filler and buzzwords", u5 went to 4/4 and u4 to 4/4, while u1 and u2 dipped to 3/4 (one miss each). u7 ("cut the filler from this product announcement") still loads 0/4 on Sonnet, which edits the text directly. Applied: the net effect is +1 on each model.
- **technical-writing under-triggers on Haiku** for tutorial and CONTRIBUTING edits (t5 2/4, t8 1/4). After naming "tutorials, how-to guides, ... CONTRIBUTING or setup docs", t5 went to 3/4 and t8 to 4/4. The current description has no UI-copy exclusion, though the body says "Product UI strings are not documentation". Sonnet loaded technical-writing for the toast-string prompt (n3) in 1 of 4 runs, and unslop in another. With "Not for product UI strings" added, Sonnet stopped, but Haiku loaded it once in 4. Applied: +4 on Haiku, and Sonnet is flat.
- **Commit messages and PR descriptions** appear in both the unslop and technical-writing descriptions. In practice they route to technical-writing every time (t7 4/4) or to nothing (t6: there is no git repository in the harness, so the model asks for the diff). No collision was observed, so this was left alone.
- **reflect** loads reliably on explicit asks (r2, r3, r4, r8, r9 all pass). It misses "make sure that sticks for future sessions" (r7). There, Sonnet reaches for `update-config` to add a hook, which reflect's own body would route to Backlog as a mechanism anyway, and Haiku just promises to remember. The `/reflect` prompt in an empty session (r1) expands the skill without a `Skill` tool call. The skill then correctly says there is nothing to reflect on, so the harness counts r1 as a miss. Ignore r1. A tighter reflect description (adding "retro" and "capture what was learned so it sticks") changed nothing, so it was not applied. The proposed wording is kept in `results/2026-10-05/proposed-descriptions/`.
- **Negatives mostly held:** "review my diff for bugs" (d8), "proofread for typos only" (n4), and "simplify this function" (n6) never loaded a phase-1 skill. "Open a PR for this branch" (d6) accepts no skill or deslop. Sonnet with the proposed descriptions loaded technical-writing for it once in 4 runs, presumably to write the PR description.

## Description changes (applied, Version 1.0.0 to 1.0.1)

- **deslop:** "from a code diff" became "from a code diff or pasted code".
- **unslop:** appended ", or when text sounds robotic, salesy, like marketing copy, or full of filler and buzzwords".
- **technical-writing:** the list now names "tutorials, how-to guides" and "CONTRIBUTING or setup docs", and the description ends with "Not for product UI strings."
- **reflect:** unchanged.

## Recommendations (skill bodies not changed)

- **unslop and technical-writing:** both say not to invent sources or jargon, but neither says "add no new facts, claims, steps, or escalation paths". In this eval, the blind grader's most common failure in every arm was an invented clause or step. A one-line rule in each Process section is the cheapest fix to try next.
- **reflect:** step 4's "show ... and stop" is right for interactive use, but it means the skill never writes a file even when told to, which breaks `claude -p` and scheduled use. Consider "If the user asked for a file, write it there too."
- **deslop:** the Opus run that inlined `clean_name` suggests adding "don't inline or remove a function other modules may import" next to the single-use-wrapper rule.

## Caveats

- One fixture per skill (two for deslop), 3 runs per cell. Differences of 3 to 5 points are within run-to-run noise.
- Sonnet and Opus are at or near the ceiling on deslop and reflect. These fixtures can't separate them.
- The LLM grader is Sonnet 5.5 grading Haiku, Sonnet, and Opus outputs, with one call per run. Its evidence strings were spot-checked and are specific, but it is strict: one added clause fails meaning_preserved or no_invented_facts.
- Graders changed after the first outputs were seen, and each change is logged in its file:
  - technical-writing v1 to v2: two artifacts were removed.
  - technical-writing v2 to v3: "You should see `ok`" is no longer counted as hedging.
  - deslop signups v2: `int(capacity)` is not scored, because nothing pins `capacity`'s type and Opus kept it on purpose with a stated reason.
  - reflect v2: declined mentions are ignored.
  
  Every change was applied to both arms and all runs. The reflect change removed the skill's apparent advantage. The others moved both arms.
- Trigger routing in `claude -p` with only the `Skill` tool is not the same as a full interactive session with other tools and history, so treat it as directional.
- Opus ran on reflect (chosen because of the v1 lift that turned out to be an artifact) and then on unslop as well. technical-writing has no Opus cell.
